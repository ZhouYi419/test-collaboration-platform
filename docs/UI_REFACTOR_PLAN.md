# 全页面 UI 重构计划

当前阶段为 T005.1 全套评审。下文保留最初的规划和试排参数，实际方案见 [全套原型](prototypes/t005/review.html)。

## 目标与范围

面向测试与开发日常协作，建立清楚、利于连续处理事项、视觉细节一致的工作界面。解决当前暖白灰绿、连续横线分节、大标题与疏松布局共同产生的纸质记录感，以及登录插画和实际工作区之间的气质落差。

绿色或暖色本身并不妨碍专业工具。此次重构需要重新验证构图、层级、信息密度与品牌气质的组合，不能把换成蓝色当作完成。

- 全部现有页面、共用导航、对话框、底部面板及加载、空、失败、权限等适用状态纳入设计。
- 沿用 PRD F001–F004 已确认的角色、字段、状态、附件、幂等和权限规则。业务实现与既有验收见 [任务记录](TASKS.md)。
- 测试验证、查询与历史、通知、统计依次由 T006–T009 规划。T005 聚焦现有能力的界面，保留账号管理分页。
- 现有 URL、登录后进入账号页、角色入口和数据访问规则沿用。若原型提出导航行为变化，单列为交互决策评审，不能随视觉改动直接实施。
- 后端 API、数据库和技术栈不因本次视觉重构调整。当前已安装 Element Plus，但界面主要使用自定义 Vue 组件；不把整体迁移组件库作为前置条件。

## 当前页面与状态清单

以 `frontend/src/main.ts`、`AuthPage.vue`、`AccountPage.vue`、`AdminAccountsPage.vue`、`IssuePage.vue`、`IssueEditor.vue`、`IssueWorkflow.vue` 为依据。一个 URL 可以包含不同的任务界面；不能只统计路由数量。

| 编号 | 页面或状态、当前入口 | 角色与主要操作 | 重构重点 |
| --- | --- | --- | --- |
| P01 | `/login` 登录 | 未登录；用户名或邮箱、密码、显隐、转注册 | 品牌与工作区统一；表单主次明确；避免插画决定全站基调 |
| P02 | `/register` 注册 | 未登录；四项填写、返回登录 | 与登录统一控件和反馈；窄屏保持合理填写节奏 |
| P03 | 注册成功，仍在 `/register` | 等待启用、返回登录并带入用户名 | 独立结果层级；保留启用约束和下一步 |
| P04 | `/account` 我的账号 | 所有可登录角色，包括未分配角色；查看与退出 | 紧凑账号信息区、清晰退出入口；不渲染成大片横线清单 |
| P05 | `/admin/accounts` 账号管理 | 管理员；分页、编辑普通账号、分配角色、启停 | 账号识别、角色、状态与行操作清晰对齐；长邮箱可完整查看 |
| P06 | P05 的编辑对话框／窄屏底部面板 | 管理员；角色与状态编辑 | 字段、停用影响、保存失败和按钮稳定；焦点与 Escape 行为保留 |
| P07 | `/admin/authorizations` 管理员授权 | 服务器操作人员；分页、授予 | 复用管理列表，区分已授予与可操作；权限入口独立于管理员角色 |
| P08 | P07 的授权确认面板 | 服务器操作人员；确认授予 | 目标账号、启用与替换原角色的后果清楚；失败可在原位重试 |
| P09 | `/issues` 我的事项 | 测试；查看本人草稿和已提交事项、新建 | 标题为主要扫读轴；类型、P0–P3、状态、时间各有稳定位置 |
| P10 | `/issues/new` 初始、Bug、需求表单 | 测试；直接提交或保存草稿 | 公共字段、类型专属字段、分配、附件按填写节奏组织 |
| P11 | `/issues/:issueId` 草稿编辑 | 草稿创建人；续编、保存、提交、删除 | 明确草稿状态；保存与提交主次；删除与放弃修改确认 |
| P12 | `/issues/:issueId` 已提交详情 | 提交人；阅读、下载附件、查看负责人和反馈 | 状态与关键属性集中；长正文可读；反馈易定位；暂不出现验证操作 |
| P13 | `/development?queue=inbox` 待领取 | 开发；查看、进入领取 | 队列切换、列表与当前任务形成连续结构 |
| P14 | `/development?queue=assigned` 我的待办 | 开发；待处理与处理中事项 | 用文字、符号和颜色区分阶段；不添加尚无接口的数量和统计 |
| P15 | `/development?queue=feedback` 已反馈 | 开发；查看已反馈结果 | 待验证仍为未闭环状态，不能用“完成”或全绿暗示已关闭 |
| P16 | `/development/:issueId` 待领取详情与确认 | 开发；阅读、下载、领取 | 先看问题与负责人状态，再采取领取；保留抢领失败后的列表反馈 |
| P17 | `/development/:issueId` 待处理详情 | 负责人；开始处理 | 关键属性、问题正文、主要动作分层；状态变化有明确反馈 |
| P18 | `/development/:issueId` 处理中详情 | 负责人；填写处理说明、提交 | 输入、字段错误、写入失败与提交位于关联区域；防止长文导致主操作失联 |
| P19 | `/development/:issueId` 已反馈详情 | 负责人；阅读处理结果 | 成功反馈与只读说明衔接；提交后焦点进入可读结果 |
| P20 | 各工作页的加载、空、加载失败 | 对应有权限角色；等待、重试或正常导航 | 保留页面身份与框架；空状态表达当前队列，不编造操作入口 |
| P21 | 无权限、事项不可用、会话失效 | 直达链接、权限变化或登录过期 | 可恢复路径清楚；不展示受限记录信息；401 沿用返回登录行为 |
| P22 | 写入、下载、候选加载失败及冲突 | 保存、提交、领取、反馈、账号维护等 | 反馈贴近可处理位置；保留既有输入和重试语义；不重复提交 |
| P23 | 共用框架与导航 | 测试、开发、管理员、服务器操作人员、未分配角色 | 统一页面宽度、导航选中态、品牌、账号身份；窄屏多入口不挤压 |

根路径 `/` 当前跳转 `/account`，未知路径经 `/` 回到账号页；它们是导航行为，不额外发明首页和 404 产品页面。原型评审工具可提供状态入口，但评审入口不进入实际产品导航。

## 建议视觉方向，待原型验证

### 构图与层级

- 工作区先于登录页定调。首先试排开发列表、处理中详情和 Bug 新建表单，覆盖扫读、阅读与输入三种任务，再扩展到全部页面。
- 桌面采用稳定导航与主工作区。页面标题、队列切换、列表／正文和主要动作形成明确层级；控制超大标题及无目的空白。
- 列表保留对齐的表格，使用浅表头、适度行距、轻分隔和明确悬停反馈。分隔线用于结构，不要求每块内容都加线或卡片。
- 详情外框与列表沿相同主工作区边线对齐；长正文独立限宽。宽屏可试排正文与关键属性分区，窄屏依阅读和操作顺序重排，具体结构由原型决定。
- 表单通过字段分组、栅格与间距表达顺序。实际结果／预期结果保留宽屏对照、窄屏顺排；附件、分配与主操作不能淹没在长文本中。
- 保留必要图标、状态线索和分组容器。删冗余文案不等于删除导航线索，避免将所有界面简化为文字加横线。

### 配色、排版与组件的初始试排值

以下用于第一轮试排，并非已确认 token；原型需要检查真实中文、数字、状态和交互对比。

| 用途 | 建议起点 | 验证重点 |
| --- | --- | --- |
| 页面底与内容表面 | 中性浅灰 `#F5F6F8`、白色 `#FFFFFF` | 容器边界可辨，避免全站纸张底色；白色也不能造成大片空洞 |
| 主文字与辅助文字 | 石墨色 `#20242D`、中性灰 `#606875` | 标题、数据、说明可扫读；正常文字对比度以至少 4.5:1 为设计验收目标 |
| 主操作与选中 | 蓝色 `#4263EB` 作为首轮候选 | 不承担成功、紧急等其他语义；焦点、悬停、按下和禁用单独验证 |
| 业务状态 | 草稿中性灰、待领取中性、待处理琥珀、处理中蓝、待验证紫 | 有文字／符号辅助，灰度下仍能区分；待验证不表示完成 |
| 优先级与反馈 | P0 红色强调；P1 适量强调，P2/P3 收敛；成功绿、错误红 | 与业务状态不混淆；不过度给整行上色；危险操作与普通操作分开 |
| 字体 | 沿用系统中文无衬线字体栈 | 中文、英文、邮箱、P0–P3、日期和数字真实试排，不为风格随意加字体依赖 |
| 字级与密度 | 工作页标题约 24–28px；正文／列表约 14px；辅助信息约 12–13px | 按内容与视口调整；不把小字号或极密布局等同于专业 |
| 控件与容器 | 控件约 6–8px 圆角，面板约 10–12px；阴影主要用于浮层 | 同用途一致；不通过统一加阴影、卡片或渐变制造质感 |
| 动效 | 局部反馈约 120–180ms，保留减少动态效果路径 | 状态变化明确、不拖慢连续操作、不导致跳动或输入丢失 |

首轮集中打磨一个有明确依据的方案。若真实工作页试排显示重要取舍，再提供差异明确的候选；不以多套换色稿代替设计判断。上一轮提出的蓝／蓝紫同样只是建议，不能未经验证升级成“企业工具必须这样配色”。

登录与注册沿用工作区字体、品牌和控件。先试排无插画的完整构图；若保留图片，必须说明它对品牌的作用，并验证与工作区连续。现有小雀不作为必须保留的资产，也不预设必须替换为科技渐变插画。

## 原型覆盖与验收证据

T005.1 的覆盖清单以 P01–P23 为索引，每项标明「可查看」「可操作」「未覆盖」「待验证」及入口。相同表现可以复用，角色结果、两类表单、不同写入错误及业务阶段应能分别进入。

| 验证组 | 必须能进入并验证的内容 |
| --- | --- |
| 身份 | 登录错误、待启用／停用提示、注册校验与冲突、提交中、网络失败、成功待启用、会话失效 |
| 账号 | 未分配角色、账号页加载与退出失败、普通账号编辑、无角色启用校验、停用影响、分页、授权与失败重试、无权直达 |
| 测试事项 | 空与有数据列表；新建初始及 Bug／需求；不完整草稿；两类提交；删除和放弃修改；只读详情与反馈 |
| 开发事项 | 三队列；待领取、待处理、处理中、待验证详情；领取取消／成功／冲突；空说明与提交失败后重试 |
| 附件与候选 | 无／有／长文件名；类型、数量、大小错误；移除与下载失败；候选加载失败、无候选、提交时候选失效 |
| 组合边界 | 长标题＋多状态＋窄屏；长字段错误＋底部操作；长处理说明＋失败提示；成功反馈出现瞬间；弹窗内容滚动 |

- 桌面：1440 × 900，并在 1280 × 800 检查列表与详情宽度和真实内容密度。窄屏：390 × 844、320 × 740；补查约 768–1024px 的导航与布局切换。超宽视口检查正文行宽。
- 数据：用接近实际的 20 条混合记录、长中英文标题、64 字符用户名、长邮箱、最长合法文件名和接近字段上限的正文试排。原型数据必须标为模拟，不能把模拟验证写成真实接口通过。
- 视觉适配：在同一视口并排检查登录、列表、详情、表单、管理页面；用户能判断它们属于同一产品。优先级、状态、主要动作与辅助属性的层级明确。
- 操作：键盘完成关键路径，检查焦点可见、确认默认取消、Escape 返回、列表恢复位置、提交成功结果焦点、减少动态效果。窄屏底部面板与操作栏不遮挡输入和反馈。
- 验收证据：每组保存代表性截图并记录入口、角色、数据、视口、实际结果和未验证项；检查失败修正后在相同条件复测。最终做整组页面复审，不能只做单页对齐检查。
- 实体手机软键盘、完整读屏与 Firefox 目前没有本轮通过证据；原型及实现时据环境实测，做不到时保留「待验收」。

## 实现边界与风险

- `styles.css` 管基础变量与认证样式，`admin.css` 同时承担框架、通用按钮／弹窗和管理页，`issues.css` 复用这些样式并覆盖工作区宽度。只替换根色变量会遗漏大量写死色值，也可能同时影响多个页面。
- 实施时将基础 token、工作区框架和实际复用的控件职责整理清楚，逐页迁移硬编码颜色。共用类逐步采用用途命名；不做与本次结果无关的大规模文件或状态管理重构。
- 按实际复用抽取导航、页面标题、按钮、反馈、状态标签、确认面板及表单控件；不同任务不强行套同一个万能页面或面板。现有 API 客户端、路由、幂等标识与业务请求流程优先保留。
- 每个实施任务运行 `frontend/` 的 `npm.cmd run build`。按变更风险执行 `backend/` 的 `..\.venv\Scripts\python.exe -m pytest -q`，后端业务未改也需在全站交付前回归现有接口与权限。PostgreSQL 测试使用独立测试库，不能以开发库替代。
- 重构没有计划中的数据结构变化，不安排数据库迁移。若实际方案确需改变 API 或业务，先记录其影响并重新核对范围。
- 当前规划阶段没有运行构建、测试或重新验收全站；旧任务的历史通过记录不作为新版 UI 的验收证据。
