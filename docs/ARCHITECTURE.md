# 技术选型与架构草案

状态：技术组合已确认，T001 已建立前端、后端及数据库结构。依据：《PRD.md》v0.3。

## 推荐技术组合
- 前端：Vue 3 + TypeScript + Element Plus，覆盖表单、列表、角色视图和状态反馈。
- 后端：Python + FastAPI，提供业务 API、参数校验和 OpenAPI 文档；采用模块化单体，不引入微服务。
- 数据库：PostgreSQL；SQLAlchemy 管理数据访问，Alembic 管理数据库迁移。
- 测试：pytest + HTTPX 做 API 测试；Playwright Python + pytest 做 Web 和端到端测试；单元测试覆盖核心业务规则。
- 工程：Docker Compose 组织本地服务；GitHub Actions 运行分层测试，生成 JUnit XML 和 HTML/Allure 报告并归档证据；GitHub Issues/PR 跟踪真实缺陷。
- 选型替代：Java + Spring Boot 更适合以 Java 企业研发岗位为目标，但学习和搭建成本可能更高；Vue 可以替换为团队熟悉的 React。

## 系统边界
浏览器 → 前端 → 后端 API → PostgreSQL。后端按身份与权限、账号、事项、处理与验证、通知、日志与统计划分模块。权限在后端校验；业务状态、处理记录与日志由后端持久化，领取和状态更新需要一致性控制。

主要实体暂定用户、会话、事项、处理记录、验证记录、附件及操作日志。状态和访问范围在对应功能细化时确定。测试准备隔离数据，避免在日志和失败证据中泄露凭据。

## 测试与运行
本地 Compose 组织开发服务，接口测试使用独立数据；CI 按风险和运行时间分层执行。Playwright 对 Firefox 和品牌版 Chrome/Edge 的运行方式依赖安装及环境，不能仅用 Chromium 代替品牌浏览器兼容性验收。GitHub 合并门禁需要额外配置仓库规则。

## T001 实现与架构评审

### 职责与依赖

- **浏览器与代理** — Vue 负责表单、状态反馈和页面导航。开发环境由 Vite 转发 `/api/`，Compose 由 Nginx 转发，浏览器在同一来源下发送请求和 Cookie。
- **身份校验** — FastAPI 负责输入校验和鉴权。登录时以 Argon2id 哈希核验密码，已启用的账号才可建立会话。`GET /api/auth/me` 每次查询会话是否有效及账号是否启用，前端据此显示账号页或返回登录。
- **数据归属** — PostgreSQL 保存用户和会话。Alembic 建库基线创建 `users` 和 `login_sessions`。数据库的唯一约束处理并发重名，注册冲突时回滚并返回错误。浏览器通过 HttpOnly、SameSite=Lax Cookie 保存令牌，数据库保存令牌摘要及到期时间。提交会话后才设置 Cookie，退出时撤销当前会话，鉴权时查询数据库。
- **账号启用** — `app.accounts enable` 使用服务操作权限直接更新账号状态，可重复执行。应用内的管理员身份、账号禁用和管理权限由 T002 接续。

### 评审结论（2026-11-15）

现有边界满足 T001 本地开发场景。Windows 本机运行的 Vue、FastAPI 和 PostgreSQL 18.3 已走通注册、启用、登录和退出。Alembic 迁移与模型差异检查、接口回归均通过。接口测试默认使用临时 SQLite 数据库，设置 `TEST_DATABASE_URL` 后在 PostgreSQL 的独立 schema 上运行。[交付与验证记录](TASKS.md)

- **运行边界** — Compose 配置使用本机回环地址、HTTP 和开发数据库凭据，容器启动待实测。若要对公网开放，评估 TLS、`SECURE_COOKIE=1`、独立凭据和登录限流，再通过实际网关复测 Cookie 和跨站请求。当前来源检查依赖浏览器提供的 `Sec-Fetch-Site`，已覆盖携带跨站标头的退出请求。
- **会话回收** — 过期会话在鉴权时立即失效。现有清理只在该账号再次登录时删除其过期会话。数据积累后可评估定期清理，验证仍有效的会话和现有退出语义。

## T002 账号状态与访问控制

- 在 `users` 保存固定角色和账号状态。建库基线 `schema_baseline.py` 直接创建当前字段和约束。已启用且未分配角色的账号可以访问个人账号页。
- 账号管理 API 复用当前用户依赖，并在服务端检查管理员角色。网页账号管理可维护普通账号。
- 服务器操作人员由后端启动配置 `SERVER_OPERATOR_USER_IDS` 绑定到当前数据库的账号 ID，权限独立于应用内角色。页面入口根据当前用户能力显示。`/api/admin/authorizations` 的读取和写入均用有效会话和服务端配置重新检查权限，授予角色并启用在同一数据库事务中提交。
- 停用账号与删除会话在同一事务中提交。PostgreSQL 对目标账号加行锁，使停用与创建会话按顺序生效。角色与状态由服务端查询，不依赖前端保存的值。

## T003 事项与附件

- 「我的事项」复用工作台，`/api/issues` 复用当前用户依赖与写操作的来源检查。后端按会话确定创建人，列表、详情、草稿变更和附件访问均校验测试角色与记录归属。
- 草稿允许业务字段缺省，转为「待领取」时检查当前类型的提交规则。创建和修改通过 `PUT /api/issues/{issue_id}` 发送表单及附件。浏览器为事项和写操作生成独立 UUID，重试沿用当前写操作 ID。服务端通过行锁和版本检查处理并发，已提交事项进入只读状态。
- 事项与附件在同一 PostgreSQL 事务中保存，附件内容独立存放，列表和详情按需读取字段与元数据。上传校验总数、大小和文件签名或文本编码。TXT、LOG 接受 UTF-8、带 BOM 的 UTF-16 和 GB18030。下载按需读取单个附件并以下载方式响应。
- `schema_baseline.py` 已包含事项及附件表。空 PostgreSQL 库的建表和模型一致性检查通过。接口回归覆盖失败回滚、并发提交和不同账号的数据隔离。

## 风险与待确认
用户技术经验、目标岗位和部署环境待确认；依赖版本、浏览器安装、CI 权限和报告保存方式实施前按官方文档及实际环境验证。首个切入点是登录注册和必要账号权限；具体注册策略和验收规则只在开始该功能时确认。
